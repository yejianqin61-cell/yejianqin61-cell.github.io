## 写在前面

我一直很向往一种工作方式：多个 Agent 并行干活，速度快，产出又能放心合并，代码库还保持干净。这篇文章整理了我围绕这个目标的一轮思考，素材来自两篇文章：

- Cursor 工程师 Lauren Tan (potetto) 关于规模化 Agent 开发的演讲，我在上一篇《从 Agent 信任到工程落地：解读 Lauren Tan 的规模化 Agent 开发方法》里做过详细解读。
- Yarchi (@undefinedKi) 的 [How to build an AI agent swarm that works without you](https://x.com/undefinedKi/status/2121240442406605251)。这篇文末标明是 Viktor 的付费赞助，产品推荐部分要打折扣，通用方法部分可以参考。

需要先说明的是，下文的盘点、拓扑和清单是我结合两篇文章做的归纳，没有经过量化验证，更适合当作起点，而不是结论。

## 1 先想清楚：瓶颈是信任

Lauren Tan 的核心观点是：并行 Agent 的数量上限，取决于你能否不逐行审查就信任它们的产出。信任不足时扩大规模，换来的只是更多低质量 PR。

两篇文章在这一点上完全一致：**信任来自独立验证，而不是 Agent 自己说"做完了"。**

| | Lauren Tan | Yarchi |
| --- | --- | --- |
| 解决的问题 | 单个 Agent 的产出能不能信 | 多个 Agent 怎么分工协作 |
| 对象 | 写代码、改代码库 | 研究、写作、文档类任务 |
| 核心手段 | `verify`、lint、结构约束 | 独立检查者、文件交接 |

从中我学到的几点：

1. **先建验证闭环，再谈并行。** 判断标准是"仅凭 diff 和证据就能决定合并"。
2. **同一个错误只纠正一次。** 第二次出现就往上升级：先改代码结构，再加 lint 规则，最后才写进规则文件。这就是 Lauren Tan 说的 correction ladder。
3. **让最省事的写法就是正确的写法。** 只保留一条推荐路径。
4. **"0 技术债"不现实。** 演讲者也没这么说。现实的目标是技术债可见、不再增长，同类错误不再重复。
5. **别急着上 swarm。** Yarchi 引用的说法是，多 Agent 的 token 消耗约为普通对话的 15 倍，而且平均来看团队并不比单个 Agent 强，只有任务能干净拆分时才占优。（这些数据来自文章引用，我没有核实。）

## 2 全链条需要哪些准备

按"从地基到并行"的顺序盘点：

### 2.0 前置条件
- **额度**：订阅制额度有限，目标是少量并行，不是上百个。
- **项目可自动运行**：一条命令启动，有测试数据，不依赖手工操作进入状态。
- **Git 基础**：主分支保护，每个任务能开独立分支和 worktree。

### 2.1 验证层（决定能不能信任）
- `verify` 命令：一次跑类型检查、lint、单元测试，退出码语义明确（0 通过，1 验证失败，2 环境错误）。
- Stop hook：要求 Agent 结束前必须跑 `verify`。
- 应用启停命令：非交互、有超时、幂等。
- UI 验证：Playwright 或 CDP 复现脚本，输出截图、日志、网络请求。
- 证据目录：固定存放，供事后查看。

### 2.2 约束层（让错误结构上难以发生）
- `CLAUDE.md` 控制在 80 行以内，只写 Agent 无法自行推断的信息。
- 纠错记录：每次纠正都记一笔，每周升级成 lint 规则或类型约束。
- 唯一推荐路径：同一件事只保留一种写法。

### 2.3 知识层（让 Agent 理解项目）
- 功能地图：功能、路由、入口文件、检查脚本的对应表。
- 常用操作封装成 CLI，而不是每次临时写脚本。
- 可以用 pstack 作起点，为项目生成验证 skill。

### 2.4 并行与审查层
- 每个任务一个 git worktree。
- 任务描述写清期望结果和验收方式，不写具体步骤。
- PR 控制在数百行以内，必须通过 `verify`。
- 可逆操作直接执行；强推、部署、删数据等必须暂停。

### 2.5 协作文件约定（借自 Yarchi）
- `BOARD.md`：任务表和共享决策。
- `tasks/`、`outputs/`、`checks/`：简报、产出、评审结果分开放。
- `LESSONS.md`：每次出问题记一行，反复出现的升级进提示词或规则后删掉。
- `NEEDS-HUMAN.md`：无人值守运行停下时把原因写在这里，我第一个打开它。

### 2.6 自动化与度量（最后做）
- 无头模式配合 GitHub Actions，让带标签的议题自动触发复现与修复。
- 同时看 PR 数、缺陷率、回退率，不能只看 PR 数。

**关口纪律**：验证层通过一个真实缺陷之前不做约束层；同类错误不再重复之前不开并行；并行稳定之前不做自动化。每个关口达标前不增加 Agent 数量。

## 3 纠错到底纠什么

"纠错"指每次纠正 Agent 时指出的任何问题，大致分四类，每类有最合适的修复位置：

| 类型 | 例子 | 修复位置 |
| --- | --- | --- |
| 不良写法 | 过时 API、绕过统一封装、临时 workaround | lint 规则；更根本的是清掉可被模仿的坏样本 |
| 架构与边界违规 | UI 直接访问数据库或 IPC、跨层 import | import 规则、目录结构、类型 |
| 边缘条件与健壮性 | 重复提交、空值、并发、超时 | 复现脚本转成回归测试；能类型化的用类型表达 |
| 流程与验证疏漏 | 没复现就修、只说"能编译"就宣布完成 | `verify`、Stop hook、playbook |

前两类最适合升级成 lint 和结构约束，边缘条件则靠测试守住。

## 4 如何清理现有技术债

Lauren Tan 给了三条原则：清理既有债、只留一条推荐路径、先阻止扩散再逐步清理。落到步骤上，我会这样做：

1. **先盘点，别急着改。** 让 Agent 扫出重复出现的坏模式和"同一件事有多种写法"的地方，按出现次数排序。
2. **挑少数高频模式**，优先选 Agent 最容易模仿的。
3. **每个模式定一种推荐写法。** 这一步由人决定。
4. **先加 lint 拦住新增。** 老代码用基线或豁免清单暂时放过。
5. **用 codemod 或脚本批量迁移**，而不是手工一处处改。
6. **小 PR 逐个模式迁移**，每个都过 `verify`，迁移完删掉对应豁免。
7. **缺测试的区域先补行为级测试**，再重构。

## 5 我的协作拓扑

我的设想是一个人统领 4 个主 Agent，其中一个专门写任务、派发分工，一个专门做对抗性评审、检查技术债。

最初我想让每个 Agent 再派发子代理，扇出到 20 多个。后来觉得太多了：Yarchi 明确建议工人不要再派发子代理，Lauren Tan 要求主 Agent 对子代理结果负责并亲自审 diff，每多一层，要核对的东西就翻倍，额度也很快耗尽。于是收敛成下面这样，总数大约 8–10 个：

| 角色 | 职责 | 子代理 | 写入范围 |
| --- | --- | --- | --- |
| 派发 | 拆任务、写简报、定共享决策 | 无 | `BOARD.md`、`tasks/` |
| 实现 A、B | 各自在独立 worktree 里完成一块 | 最多 2–3 个 | 各自分支和 `outputs/` |
| 评审（对抗性） | 只读 diff 和证据，查技术债和结构问题 | 无 | `checks/` |
| 合并与清债（可选） | 合并通过的分支，更新 `LESSONS.md`，把重复问题转成 lint | 无 | 主分支、规则文件 |

几条硬规则：

- 每个文件只有一个写入者，每块任务只有一个负责人。
- 评审 Agent 必须是新会话，最好换模型，只拿简报、diff 和证据，不看实现过程。
- 评审是模型意见，不是验证。真正的门槛仍是自动化的 `verify`，评审排在它之后。
- 每块任务最多返工两轮，之后交给我。

### 5.1 主 Agent 要对子代理的产出负责

potetto-mode 有一条规定：主 Agent 对子 Agent 的结果负责，需要审查 diff 并自行撰写总结，不转述子 Agent 的自述。

意思是主 Agent 要亲自审查子代理的实际产出，而不是根据子代理的反馈来总结。反馈只是子代理对自己工作的描述，常见的偏差有：

- 说"已修复并测试通过"，但测试其实没跑，或者跑的是别的测试。
- 说"只改了 A 文件"，实际顺手改了 B。
- 遇到困难时悄悄缩小了任务范围，汇报里不提。
- 把猜测写成结论。

主 Agent 如果只转述这些话，错误会原样传上来，而且经过一层"总结"后看起来更可信。所以主 Agent 要做四件事：

1. **看 diff**：实际改了哪些文件、哪些行，是否超出任务简报的范围。
2. **看证据**：`verify` 的输出、截图、复现脚本的结果，确认确实运行过。
3. **自己写总结**：基于 diff 和证据写，把子代理的说法当线索，不当结论。
4. **再决定下一步**：合并、返工，还是交给我。

这会消耗主 Agent 的上下文和额度，这也是子代理不宜派太多的原因。几个让审查更省力的办法：子代理传文件路径而不是内联内容；`verify` 输出结构化摘要加日志路径；PR 保持小粒度，几百行的 diff 才审得过来。

同样的道理也适用于我自己：我对 4 个主 Agent 负责，也不能只看它们的汇报，而要看 `checks/` 里的评审结果、`verify` 的证据和最终 diff。

## 6 技术债检查清单

给评审 Agent 一份明确的清单，否则它容易泛泛而谈。下面是我整理的 Agent 最容易引入技术债的错误，同样是经验归纳，不是统计排名。"自动"表示能用 lint 或脚本拦截，"评审"表示需要判断。

### 6.1 复制与重复
| # | 错误 | 典型表现 | 检测 |
| --- | --- | --- | --- |
| 1 | 复制邻近的 workaround | 把临时补丁当标准写法照抄 | 评审 |
| 2 | 重新实现已有工具函数 | 新写一个 `formatDate`，项目里早就有 | 评审 + 重复代码检测 |
| 3 | 同一件事引入第二种写法 | 项目有 fetch 封装，它直接用 axios | 自动：禁用指定 import |
| 4 | 为小问题新增依赖 | 为一个函数引入整个库 | 自动：检查依赖变更 |

### 6.2 绕过约束
| # | 错误 | 典型表现 | 检测 |
| --- | --- | --- | --- |
| 5 | 类型逃逸 | `any`、`as unknown as`、`@ts-ignore` | 自动 |
| 6 | 关闭或豁免 lint | `eslint-disable`、扩大基线 | 自动：新增豁免即拦截 |
| 7 | 改测试迁就实现 | 改断言、删测试、加 `skip` | 自动：断言减少或出现 skip 时标记 |
| 8 | 吞掉异常 | 空 `catch`、只打日志继续 | 自动 + 评审 |
| 9 | 只修症状 | 加判空、重试、延时掩盖根因 | 评审：要求说明根因 |

### 6.3 结构与边界
| # | 错误 | 典型表现 | 检测 |
| --- | --- | --- | --- |
| 10 | 跨层调用 | UI 组件直接访问数据库或 IPC | 自动：import 边界规则 |
| 11 | 改动范围扩散 | 修一个 bug 顺手重构三个文件 | 自动：PR 规模上限；评审对照简报 |
| 12 | 过度抽象 | 为一处用法建接口、工厂、配置项 | 评审 |
| 13 | 继续往大文件里堆 | 800 行的文件再加 200 行 | 自动：文件长度和复杂度阈值 |
| 14 | 硬编码 | 魔法数字、写死的路径、URL、密钥 | 自动 + 密钥扫描 |

### 6.4 遗留物
| # | 错误 | 典型表现 | 检测 |
| --- | --- | --- | --- |
| 15 | 死代码 | 旧实现留着"以防万一" | 自动：未使用代码检测 |
| 16 | 调试残留 | `console.log`、临时文件 | 自动 |
| 17 | TODO 不登记 | `// TODO: fix later` 无人跟进 | 自动：新增 TODO 须带任务编号 |
| 18 | 为补丁辩护的注释 | 解释"这里为什么要特殊处理" | 评审：往往标记着该修掉的问题 |

### 6.5 验证不充分
| # | 错误 | 典型表现 | 检测 |
| --- | --- | --- | --- |
| 19 | 以代理指标宣布完成 | "能编译""测试通过"，没跑真实场景 | 要求附证据 |
| 20 | 只测快乐路径 | 没有错误分支和边界条件 | 评审 |
| 21 | 测试迎合实现 | 断言就是实现的复述 | 评审：测试是否基于需求 |

用法：

1. 能自动化的条目先交给 lint 和脚本，不让评审 Agent 去做。
2. 评审 Agent 只负责需要判断的条目，每条意见附文件和行号，并标注是测得、推断还是猜测。
3. 同一条问题出现第二次就升级为规则，清单因此会越用越短。

## 7 需要借助的外部工具

整体原则来自 Lauren Tan：本地开发和验证优先用 CLI，MCP 留给需要认证的远程服务。所以下面大部分是普通的命令行工具。

这份清单是我根据已知信息整理的。pstack 和 cursor-team-kit 的安装方式出自它们的 README，其余工具我还没在自己的项目里实际验证过，版本和兼容性以各自文档为准。

### 7.1 插件与 skill（方法论和现成流程）

| 名称 | 用途 | 说明 |
| --- | --- | --- |
| pstack（cursor/plugins） | potetto-mode、playbook、原则、验证 skill 生成器 | 可在 Claude Code 中安装；依赖 Cursor 专有功能（Bugbot、automations）的步骤会被跳过 |
| cursor-team-kit | control-ui、control-cli，用于 UI 和 CLI 的复现与验证 | pstack 建议一起安装 |
| pstack-claude | 社区移植版，面向 Claude Code、Codex | 可替代 pstack，非官方 |

### 7.2 MCP（只在 CLI 不够用时）

| 名称 | 用途 | 是否必需 |
| --- | --- | --- |
| Playwright MCP 或 Chrome DevTools MCP | 让 Agent 交互式地操作浏览器、查看页面 | 可选，写成 Playwright 脚本通常更稳定、可复现 |
| GitHub MCP | 读写议题和 PR | 可选，`gh` CLI 已经够用 |

### 7.3 Claude Code 自带的能力

- Hooks：用 Stop hook 强制 Agent 结束前跑 `verify`。
- 子代理和 git worktree：并行与隔离。
- 无头模式 `claude -p`：配合 GitHub Actions 做自动化。
- `CLAUDE.md`、规则文件、自定义 skill：存放项目知识和自己的验证 skill。

### 7.4 普通开发工具（验证层和技术债清单靠它们）

| 用途 | 工具（JS/TS 生态举例） |
| --- | --- |
| UI 复现脚本 | Playwright |
| Lint 与类型 | ESLint、TypeScript |
| 重复代码 | jscpd |
| import 边界 | dependency-cruiser |
| 死代码、未用依赖 | knip |
| 密钥扫描 | gitleaks |
| GitHub 操作 | `gh` CLI |

### 7.5 引入顺序

1. 第一周只装 pstack 和 cursor-team-kit，加上 Playwright 和项目原有的 lint、测试。
2. 纠错层级跑起来后，再按需加 knip、dependency-cruiser 等检测工具。
3. MCP 先不装，等确实遇到 CLI 解决不了的场景再加。

## 8 下一步

我打算先花一周只做一件事：给自己的项目写好 `verify`，再用一个真实缺陷跑通"复现、修复、验证"。这一步通了，再按上面的拓扑加并行，并观察额度消耗和返工次数，决定要不要放大。
