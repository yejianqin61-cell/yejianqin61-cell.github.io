# 计算机网络知识日志 01：从 Linux 路由表理解 IPv4 寻址、转发与 NAT

> 日期：2026-11-02（MYT）  
> 学习来源：小林 Coding《图解网络》与围绕 `route -n` 的问答  
> 主题：TCP/IP 网络层、IPv4、子网、路由选择、ARP、网关、NAT 以及 TCP 发送路径

## 0. 今日问题的起点与最终认知

一开始的问题是：Linux 执行 `route -n` 后，`Destination`、`Gateway`、`Genmask` 分别是什么意思？

探索过程中，逐步消除了这些混淆：

- `192.168.x.x` **不是“必然属于本机的 IP”**，而是位于私有 IPv4 地址范围中的一种地址；它也可能是室友电脑、局域网 Web 服务器或网关的地址。
- `Destination` 通常表示**路由条目匹配的目标网络前缀**，而不是某台 Web 服务器的 IP，更不是源主机 IP。
- `Gateway` 表示**下一跳路由器**；`Gateway=0.0.0.0` 在传统 `route -n` 展示中通常表示该路由不指定网关、属于直连（on-link）路由。
- `Destination=0.0.0.0` 且 `Genmask=0.0.0.0` 表示**默认路由 `0.0.0.0/0`**，而不是“默认网卡”。真正的出口接口看 `Iface`。
- 访问公网 IP 时，**不是先由宿舍路由器把公网目标地址变成私有地址再让电脑选网卡**。源主机先查本机路由；在常见的 IPv4 家庭 NAT 环境中，网关随后转换**源私有 IP（和通常的源端口）**，公网目标地址通常保持不变。

**一句话心智模型**：应用程序决定与谁通信 → 网络层按目标 IP 查路由 → 确定下一跳与出口接口 → 链路层将帧送往下一跳 → 中间路由器逐跳转发，必要时执行 NAT → 最终主机接收。

## 1. 网络中的“地址”与网络范围

### 1.1 本机 IP（Local IP / Interface Address）

本机 IP 是**配置给当前设备网络接口的 IP 地址**，不是一种特殊的地址段。一台主机可同时拥有多个 IP：

| 设备或接口      | IPv4 地址           | 含义                             |
| --------------- | ------------------- | -------------------------------- |
| 本机 `eth0`     | `192.168.3.100/24`  | 本机第一张网卡的地址             |
| 本机 `eth1`     | `192.168.10.100/24` | 本机第二张网卡的地址             |
| 内网 Web 服务器 | `192.168.10.200/24` | **另一台设备**的地址             |
| 云服务器        | `159.75.219.30`     | 用于示例的远程服务器公网目标地址 |

`ip addr` 可以查看本机实际接口地址；网卡名也可能是 `wlan0`、`enp3s0`、`ens33` 等。

### 1.2 源 IP 与目标 IP

在一个出站 IP 数据包中：

- **Source IP（源 IP）**：IP 层认定的发送者地址。通常由操作系统根据路由、地址配置及应用的绑定行为选择。
- **Destination IP（目标 IP）**：最终要到达的目的主机地址。常规路由转发**不会**把它替换成网关地址。

例如向云服务器发送数据包：

```text
Source IP:       192.168.1.100
Destination IP:  159.75.219.30
```

### 1.3 私有 IP、公网 IP 与环回 IP

| 类型      | 地址或范围                      | 核心意义                                         |
| --------- | ------------------------------- | ------------------------------------------------ |
| 私有 IPv4 | `10.0.0.0/8`                    | 可在独立私有网络内复用                           |
| 私有 IPv4 | `172.16.0.0/12`                 | 范围为 `172.16.0.0`～`172.31.255.255`            |
| 私有 IPv4 | `192.168.0.0/16`                | 常见于家庭、宿舍和企业内网                       |
| 环回 IPv4 | `127.0.0.0/8`，常用 `127.0.0.1` | 访问本机 TCP/IP 协议栈，不发到物理网卡           |
| 公网 IPv4 | 可在全球公网路由的已分配地址    | 可以通过互联网路由到相应网络，但不保证服务可访问 |

重要辨析：

- “私有”是**地址用途分类**；“本机”是**地址配置归属**，二者不是同一维度。
- 内部 Web 服务可以有私有 IP；面向公众的 Web 服务可以有公网 IP、负载均衡入口或代理入口。
- `203.0.113.10` 属于**文档保留示例地址**（TEST-NET-3），不是实际可用于公网部署的普通地址；本文只用它做 NAT 演示。
- 私有地址不能直接在公共 IPv4 互联网中路由；但不同私有网络之间可以借助专线、VPN、内部路由等互通，**并不是任何跨网段私有通信都必须 NAT**。

### 1.4 网络地址、主机地址和 CIDR

`192.168.10.200/24` 中：

- IP：`192.168.10.200`，标识具体接口地址。
- `/24`：前 **24 位**为网络前缀，等价于掩码 `255.255.255.0`。
- 对应网络前缀：`192.168.10.0/24`。
- 该路由前缀匹配 `192.168.10.0`～`192.168.10.255`；在传统 `/24` 子网中，一般的可用主机地址是 `.1`～`.254`，`.0` 是网络地址，`.255` 是定向广播地址。

**网络地址不是另一台真实主机的地址**；它是在一定掩码下，对一组 IP 地址的统一表示。

## 2. 子网掩码（Genmask / Subnet Mask）到底干什么？

### 2.1 核心用途：对目标地址做路由前缀匹配

传统路由表中可以把匹配理解为：

```text
(目标 IPv4 地址 AND 该路由的 Genmask) == Destination
```

这里的 `AND` 是逐位二进制**按位与**，不是逻辑上的“且”。

假设：

```text
目标 IP        192.168.10.200
Genmask       255.255.255.0
按位 AND 结果  192.168.10.0
Destination   192.168.10.0
```

结果相等，该路由匹配。

若目标为云服务器 `159.75.219.30`：

```text
目标 IP        159.75.219.30
Genmask       255.255.255.0
按位 AND 结果  159.75.219.0
Destination   192.168.1.0
```

不相等，所以不匹配 `192.168.1.0/24`。

### 2.2 `/24` 为什么等于 `255.255.255.0`？

```text
二进制子网掩码：11111111.11111111.11111111.00000000
十进制子网掩码：255     .255     .255     .0
                   ← 24 个 1 →
```

掩码为 1 的位保留，掩码为 0 的位清零，因此按位与结果就是目标 IP 对应的**网络前缀地址**。

| 路由前缀            | 代表的匹配范围                             |
| ------------------- | ------------------------------------------ |
| `192.168.1.0/24`    | `192.168.1.0`～`192.168.1.255`             |
| `192.168.0.0/16`    | `192.168.0.0`～`192.168.255.255`           |
| `192.168.1.128/25`  | `192.168.1.128`～`192.168.1.255`           |
| `0.0.0.0/0`         | 全部 IPv4 地址                             |
| `192.168.10.200/32` | 仅 `192.168.10.200` 这一个地址（主机路由） |

### 2.3 最长前缀匹配（Longest Prefix Match）

可能有**多条路由同时匹配**同一个目标 IP，例如：

```text
192.168.0.0/16    via 192.168.1.1
192.168.1.0/24    dev wlan0
0.0.0.0/0         via 192.168.1.1
```

对目标 `192.168.1.200`，三条都匹配；通常选择更具体的 `/24` 路由。`/0` 是兜底，不是“不需要判断的默认网卡”。只有在前缀长度等路由选择条件相当时，才进一步考虑优先级、metric、策略规则等因素。

## 3. Linux 路由表的四个核心字段

示例（假设）：

```bash
$ route -n
Kernel IP routing table
Destination     Gateway         Genmask         Flags Metric Ref Use Iface
192.168.3.0     0.0.0.0         255.255.255.0   U     100    0   0   eth0
192.168.10.0    0.0.0.0         255.255.255.0   U     100    0   0   eth1
0.0.0.0         192.168.3.1     0.0.0.0         UG    100    0   0   eth0
```

| 字段          | 中文       | 应该问自己的问题                           |
| ------------- | ---------- | ------------------------------------------ |
| `Destination` | 目标网络   | 这条规则覆盖哪些目的 IP？                  |
| `Genmask`     | 子网掩码   | 如何判定目标 IP 是否匹配？                 |
| `Gateway`     | 下一跳网关 | 选中这条路由后，把包交给哪个下一跳路由器？ |
| `Iface`       | 出口接口   | 从本机哪个接口发出？                       |

补充字段：

- `Flags=U`：路由有效/启用；`G`：使用网关。
- `Metric`：路由优先级相关的代价值；不取代最长前缀原则。
- `Ref`、`Use` 是旧式显示字段，现代 Linux 上不必把它们当作可靠的实时转发统计。

### 3.1 `0.0.0.0` 不同位置，不同含义

| 出现形式                               | 含义                                                     |
| -------------------------------------- | -------------------------------------------------------- |
| `Destination=0.0.0.0, Genmask=0.0.0.0` | 默认路由，CIDR 表示 `0.0.0.0/0`                          |
| `Gateway=0.0.0.0`                      | 当前条目没有指定下一跳网关，通常直接在相应链路上寻找目标 |
| `Iface=eth0` / `wlan0`                 | 实际的出口接口；不由 `0.0.0.0` 单独表示                  |

### 3.2 网关到底是什么？

Gateway 是**这一步的数据包应该交给的下一跳路由器**，它不是最终 Web 服务器。

访问 `159.75.219.30` 时，可能是：

```text
Linux 192.168.1.100
  └─ 经 wlan0 → 网关 192.168.1.1
       └─ 运营商网络 → 若干中间路由器 → 159.75.219.30
```

送到第一跳时：

- **IP 头目的地址**：仍然是 `159.75.219.30`。
- **链路层帧的目的 MAC**：通常是网关 `192.168.1.1` 所对应的 MAC。

路由器收到数据包后，继续查看它**自己的**路由表，决定下一跳。

## 4. 路由表是如何生成的？

路由表不是访问一个网站之后才“注册一条网站 IP”。正常情况下，相关规则早已随网络配置存在；一次访问主要是查找并选择它们。

### 4.1 接口地址配置 → 内核直连路由

假设执行：

```bash
sudo ip addr add 192.168.10.100/24 dev eth1
sudo ip link set eth1 up
```

通常会出现主路由表中的直连路由：

```text
192.168.10.0/24 dev eth1 proto kernel scope link src 192.168.10.100
```

含义：

- `dev eth1`：从 `eth1` 发送。
- `proto kernel`：由内核根据网络地址配置产生。
- `scope link`：视为链路直连网络。
- `src`：该路由建议的源 IP 地址。

并非每个地址配置都必然产生该路由（例如可以用 `noprefixroute` 抑制自动前缀路由），具体看配置方式。

### 4.2 DHCP → 网络管理组件安装地址和路由

例如 DHCP 分配：

```text
IP = 192.168.1.100
Mask = 255.255.255.0
Default gateway = 192.168.1.1
```

最终可能得到：

```text
192.168.1.0/24 dev wlan0 proto kernel scope link
 default via 192.168.1.1 dev wlan0
```

DHCP 提供配置参数；由系统的 DHCP 客户端、NetworkManager、systemd-networkd 等将配置应用到内核。

### 4.3 静态路由：管理员明确指定

```bash
sudo ip route add 10.20.0.0/16 via 192.168.1.1 dev wlan0
```

表示：访问 `10.20.0.0/16`，下一跳是 `192.168.1.1`。

### 4.4 VPN、动态路由、接口变化

- 启动 VPN 可能新增虚拟网卡和专用路由，甚至替换默认路由。
- 路由器或安装了路由软件的 Linux 主机可能使用 OSPF、BGP 等协议学习路由，并将结果安装到路由/转发表中。
- 接口上下线、IP 更换、配置更新，均可能触发路由增删改。
- Linux 还支持策略路由：多张路由表、`ip rule` 等；`route -n` 并不展示全部策略决策过程。

## 5. 全部典型通信链路 Case（按目标和转发机制分类）

> 统一假设：下述 IP、网卡、网关和 NAT 设置是为了演示，实际网络必须以 `ip addr`、`ip route` 输出为准。这里区分“选路”“ARP”“NAT”，避免把它们混成一件事。

### Case A：同一子网，直连访问局域网 Web 服务器

**场景**：

```text
Linux：192.168.10.100/24（eth1）
Web：  192.168.10.200/24
路由：192.168.10.0/24 dev eth1
```

**链路**：

1. 应用发起到 `192.168.10.200:80` 的连接。
2. Linux 对目标 `192.168.10.200` 进行路由匹配，命中 `192.168.10.0/24`。
3. 该路由是直连，不需要交给三层网关。
4. Linux 用 ARP（如无缓存）解析 **192.168.10.200 自己的 MAC**。
5. `eth1` 将以太网帧发送到 Web 服务器，随后 TCP 握手、HTTP 数据交换。

**重点**：两台主机都是私有 IP；不需要 NAT。

### Case B：同一主机有两张网卡，选不同直连网络

```text
eth0：192.168.3.100/24  → 192.168.3.0/24
eth1：192.168.10.100/24 → 192.168.10.0/24
```

- 访问 `192.168.3.200` → 选 `eth0`。
- 访问 `192.168.10.200` → 选 `eth1`。

**重点**：不是“目标 IP 和本机某 IP 的文字前缀看起来一样”就随便选接口，而是**以实际路由表为准**。由于配置了直连路由，二者在此例中才刚好对应。

### Case C：目标不在本地网段，通过默认网关去公网

**场景**：

```text
Linux： 192.168.1.100/24（wlan0）
网关：  192.168.1.1
远端：  159.75.219.30（云服务器）
路由：  192.168.1.0/24 dev wlan0
        default via 192.168.1.1 dev wlan0
```

**链路**：

1. 应用要访问 `159.75.219.30`。
2. 不匹配 `192.168.1.0/24`，但匹配 `0.0.0.0/0`。
3. Linux 选择 `wlan0`，下一跳 `192.168.1.1`。
4. ARP（如无缓存）解析的是**网关的 MAC**，而不是远端服务器的 MAC。
5. 数据帧到达路由器；随后由路由器和其他网络逐跳转发。

**重点**：在此场景，**网关 IP 是当前下一跳，但 IP 头的目的 IP 依旧是 `159.75.219.30`**。

### Case D：出站访问公网 + NAT（家用/宿舍典型）

继续 Case C，假设宿舍网关拥有可用于公网转发的 IPv4 地址 `203.0.113.10`（仅示例）：

```text
NAT 之前：192.168.1.100:51000 → 159.75.219.30:80
NAT 之后：203.0.113.10:62000 → 159.75.219.30:80
```

源 IP（以及通常的源端口）被转换；**目标 IP 没有变成私有地址**。网关维护转换映射，使返回的数据包能够送回源主机。

> `203.0.113.10` 是保留给文档的例子，并非真的分配给宿舍路由器。宿舍网络可能还使用多级 NAT / CGNAT，原理类似但链路更复杂。

### Case E：公网服务器回应内网客户端（NAT 回程）

**链路**：

1. 服务器向 NAT 对外显示的地址与端口回复，例如 `203.0.113.10:62000`。
2. NAT 设备查先前建立的映射，识别应交给 `192.168.1.100:51000`。
3. NAT 改写返回包的目标 IP/端口，并把它转入内网。
4. Linux 客户端接收属于自己 TCP 连接的响应。

**重点**：出站和回程的 NAT 修改方向不同；它们共用先前建立的映射状态。

### Case F：公网用户访问私有网络里的 Web 服务器（端口转发 / DNAT）

**场景**：

```text
公网入口：203.0.113.10:80（示例）
内网 Web：192.168.10.200:80
端口转发：203.0.113.10:80 → 192.168.10.200:80
```

**链路**：

1. 外部客户端访问公网入口地址和端口。
2. 网关使用预先配置的 DNAT/端口转发，将**目标 IP** 改成 `192.168.10.200`。
3. 网关在私有网络内转发到 Web 服务器；回程通过相应的连接跟踪/NAT 规则处理。

**与 Case D 区别**：出站 SNAT 改源地址；这种入站 DNAT 改目标地址。需要相应的公网可达性、防火墙和端口规则；在 CGNAT 场景一般不能直接控制上游公网端口映射。

### Case G：两个不同的私有网段，经过内部路由器互通（不做 NAT）

```text
主机 A：192.168.3.100/24
路由器：eth0=192.168.3.1，eth1=192.168.10.1
主机 B：192.168.10.200/24
```

**链路**：

1. A 访问 `192.168.10.200`，目标不在本地 `192.168.3.0/24`。
2. A 使用内部路由（专门静态路由或默认路由），把包交给 `192.168.3.1`。
3. 路由器根据自己的直连路由，从 `eth1` 发往 `192.168.10.200`。
4. B 需要有正确的**回程路由**，通常通过 `192.168.10.1` 回复。

**重点**：两端都是私有 IP，也可以通过三层路由器通信，不需要 NAT。

### Case H：访问本机 `127.0.0.1`（Loopback）

```bash
curl http://127.0.0.1:3000
```

连接的是**当前机器自身**在回环接口上监听的服务，不会通过宿舍路由器，不需要 ARP/NAT。即便程序通过 TCP 通信，也仍在本机协议栈内完成。

### Case I：服务器就是本机的另一个接口地址

如果 `192.168.10.200` **真的配置在本机某个接口上**，访问它会按 Linux 的本地地址路由机制在本机处理，通常不会像访问外部主机那样真的向网络发帧。这与“访问其他设备的 `192.168.10.200`”完全不同。

### Case J：没有任何可用路由

如果路由表只有：

```text
192.168.1.0/24 dev wlan0
```

却要访问 `159.75.219.30`，且没有其他匹配路由/策略，那么内核没有转发路径，可能直接报告 `Network is unreachable`。**并不是所有 Linux 机器一定有默认路由。**

### Case K：多条路由都匹配时的选择

```text
192.168.0.0/16 via 192.168.1.1
192.168.1.0/24 dev wlan0
0.0.0.0/0 via 192.168.1.1
```

访问 `192.168.1.200` 选 `/24`，因为它是更长的前缀。只有相同优先程度下才进一步讨论 metric 等其他因素。

### Case L：VPN 改变路径

连接 VPN 后，系统可能添加：

```text
10.8.0.0/16 dev tun0
```

于是访问 `10.8.1.25` 可能走 `tun0`，而普通公网目标仍走宿舍默认网关。全隧道 VPN 还可能让公网流量也走 VPN。**VPN 之所以改变访问路径，是因为接口、路由和策略发生变化。**

## 6. TCP、IP、ARP 与 NAT 的职责边界

| 层次/机制               | 解决的问题                                  | 典型对象                   |
| ----------------------- | ------------------------------------------- | -------------------------- |
| 应用层 HTTP             | 请求哪项 Web 资源、如何响应                 | URL、HTTP 请求/响应        |
| 传输层 TCP              | 可靠、有序传输，连接建立，端口区分          | SYN、ACK、源/目的端口      |
| 网络层 IP               | 端到端 IP 寻址、选择路由、逐跳转发          | 源/目的 IP、路由表、TTL    |
| 链路层 Ethernet / Wi-Fi | 将一帧送到当前链路上的下一跳                | MAC 地址、数据帧           |
| ARP（IPv4）             | 为链路上下一跳 IP 解析 MAC                  | ARP 缓存、ARP 请求/应答    |
| NAT                     | 在网络边界按规则转换源/目标地址及可能的端口 | SNAT、DNAT、NAPT、映射状态 |

**不是建立 TCP 连接之后才需要路由**：首次 SYN 数据包就需要选路；UDP、ICMP 等其他 IP 流量同样需要路由。已建立连接可能缓存路由相关信息，不意味着每一个包都必须重新从头遍历路由规则。

**IP 与 MAC 的关键区别**：去远端公网服务器时，IP 目的地址通常一路保持为远端服务器，但每跳使用的链路层帧头（例如目标 MAC）会随下一跳改变；IP 的 TTL/Hop Limit 在路由转发时也会变化。NAT 是一个可额外修改 IP 地址的机制。

## 7. 今天所有主要误区的纠正

| 容易产生的想法                            | 更准确的理解                                               |
| ----------------------------------------- | ---------------------------------------------------------- |
| `192.168` 开头就是“本机 IP”               | 它是私有地址范围；具体是否本机要看配置归属                 |
| `Destination` 就是 Web 服务器的完整 IP    | 通常是路由前缀；也可有 `/32` 单一目标主机路由              |
| `192.168.10.0` 是一台计算机               | `/24` 情况下它表示网络前缀                                 |
| 只有目标与本机 IP 前几段相同才能通信      | 目标可经网关走向其他网络，以路由表匹配为准                 |
| 访问公网前，路由器把公网目标映射成私有 IP | 常见出站 NAT 改的是私有**源**地址；DNAT 才可能改目标       |
| `Gateway=0.0.0.0` 就是默认网卡            | 表示未指定下一跳网关，通常是直连路由                       |
| `Destination=0.0.0.0` 就是默认网卡        | 配合 `/0` 才是默认路由；出口看 `Iface`                     |
| 子网掩码仅用来判断是不是同一个宿舍网络    | 其本质还用于路由前缀匹配和路由范围表达                     |
| 连接建立之后才查询路由                    | 第一个 TCP SYN 包发送时已经需要选路                        |
| Web 服务器必须有公网 IP                   | 内网 Web 服务器可使用私有地址，公网服务可经代理/NAT 等暴露 |
| 路由表记录了所有在线的 IP 设备            | 它记录转发路径/规则，而不是活跃设备清单                    |
| 两个不同私有网段通信必须 NAT              | 正常三层路由即可，NAT 不是必需条件                         |

## 8. Linux 实践：把概念与真实输出对应起来

```bash
# 查看本机接口、IPv4/IPv6 地址
ip addr

# 查看 IPv4 主路由表（现代 Linux 推荐）
ip -4 route

# 老式路由表展示
route -n

# 询问 Linux：发送到自己的云服务器会走哪条路由？
ip -4 route get 159.75.219.30

# 查看本机 ARP/邻居缓存
ip neigh

# 查看路由策略规则（多路由表时特别有用）
ip rule

# 查看所有路由表（进阶）
ip route show table all
```

一个可能的输出：

```text
$ ip -4 route get 159.75.219.30
159.75.219.30 via 192.168.1.1 dev wlan0 src 192.168.1.100 uid 1000
    cache
```

读取方法：

- `159.75.219.30`：目标 IP。
- `via 192.168.1.1`：下一跳网关。
- `dev wlan0`：出口网络接口。
- `src 192.168.1.100`：当前路由选择使用的源 IP。

> 这只是**示意输出**，实际设备输出可能不同，甚至没有 `cache` 行；现代 Linux 内核不再采用旧式的全局 IPv4 路由缓存模型。不要把终端示例误当成你自己机器的真实配置。

### 建议实验

1. 在 Linux 上运行 `ip -4 addr` 和 `ip -4 route`，找出本机 IP、直连网段和默认网关。
2. 运行 `ip -4 route get 159.75.219.30`，解释输出的 `via`、`dev`、`src`。
3. 对比 `ip -4 route get <某个同网段设备IP>`，观察是否省略 `via`。
4. `ping` 一台已确认同网段且允许 ICMP 的主机，再检查 `ip neigh`；分析它记录的是下一跳 MAC，而不是整条互联网路径。
5. 若设备允许，比较连接 VPN 前后的 `ip route`；注意不要随意改动宿舍或生产服务器上的路由配置。

## 11. 一页速记

```text
IPv4 私有地址 ≠ 本机地址
Web 服务器可以在局域网，也可以在公网

路由匹配（概念上）：
  (目标 IP AND Genmask) == Destination
  多条匹配 → 选最长前缀（再考虑其他规则）

Destination → 这条路由覆盖哪个目标网络？
Genmask     → 匹配范围有多大？
Gateway     → 下一跳路由器是谁？
Iface       → 从哪个本地网卡发送？

Destination=0.0.0.0 + Genmask=0.0.0.0 → 默认路由
Gateway=0.0.0.0 → 不指定下一跳网关，通常直连

去同一链路的目标：ARP 解析目标主机 MAC
去异网段的目标：ARP 解析下一跳网关 MAC
正常 IP 转发：最终目标 IP 通常不变
常见出站 NAT：私有源 IP → NAT 公网出口 IP
常见入站端口转发：公网入口目标 IP → 内网服务器 IP

先配置网络接口/获取路由 → 才能发送首个 TCP SYN
```

**今日结论**：理解路由的关键，不是机械背诵 `route -n` 的列名，而是把 **目标 IP → 前缀匹配 → 下一跳/出口 → ARP → 转发 →（可能的）NAT** 串成一条可以自己解释、可以在 Linux 中验证的完整路径。

工具调用，记忆机制，推理与纠错

### 记忆机制

Agent系统通常会设计短期记忆和长期记忆两层。

短期记忆就是：当前任务执行过程中的中间状态

长期记忆就是：跨任务的，比如说用户的偏好，历史操作记录，通常使用向量数据库来存储。也就是RAG，需要的时候使用语义检索拿回来



### 多步推理和自我纠错

边做边反思，感知到失败，会分析原因，换一种方法。



## 最新趋势

anthropic再2024年给出的MCP（model context protocol）模型上下文协议

可以理解成Agent工具世界的USB-C接口



MCP就是定义一套标准的JSON-RPC协议，

工具提供方只需要按这个标准暴露自己的能力，变成一个MCP server，

任何支持MCP的agent，通过内置的MCP client，都能直接发现和调用这些工具，不需要额外写适配代码。



### MCP的架构

#### 最外层

Host，就是用户直接交互的AI应用，比如说Codex这些

#### 中间

是client层，负责和MCP server建立链接，管理通信



#### Server层

也就是最里面那层。

通过JSON-RPC协议和client层通信，负责工具提供与实现





工具提供方只需要实现一次server，所有支持MCP的Host都可以直接用







### A2A

AgentToAgent，意思是agent间的通信。

MCP让每个agent都能方便地伸手拿工具，A2A让不同的agent能够方便地互相说话合作。

未来的agent生态大概是两个协议同时存在，各管一层的格局







## Agent的基本架构

LLM,工具，记忆，规划模块



#### LLM

就是大脑，

system prompt会告诉agent的人格和行为规则



#### 什么时候用推理大模型，什么时候用小模型？

核心决策，任务规划，关键判断时，用推理能力强的大模型。

简单任务，用小模型



工具调用的稳定性，有些模型生成的JSON格式经常出错，参数乱填



模型上下文窗口，如果窗口太小，复杂任务不好跑



所以要根据任务复杂度，延迟要求，成本预算来做权衡



### 工具

工具定义里，咩有一行执行逻辑，只有名字，描述，参数说明。LLM读完之后，决定要调哪个工具，参数填什么，把决策用JSON告知



工具描述的质量，直接影响Agent的表现。

因此，工具描述需要反复调优，它的重要性不亚于prompt工程。





### 记忆系统

#### 顶层：记忆类型

语义记忆（事实）：比如说用户是做金融行业的

情景记忆（经历）：存的是具体经历，比如说上次用户问退款问题时，我们查了订单系统

程序性记忆（方法论）：类似skill



### 中层：长期记忆

向量数据库，跨任务保留

把重要信息embedding之后存起来，下次用的时候做语义检索拿回来



##### 挑战在于

什么该存，什么不该存？存了之后怎么管理？

比较好的办法是，在存入之前做一轮重要性评估，只把真正有价值的信息持久化

还有一个容易忽略的机制是，记忆衰减

给每条记忆加一个时间权重，越久远的记忆权重越低。

具体实现上大概使用一个指数衰减公式。衰减速度可以根据业务场景调整，比如客服场景衰减快一点，法律合规场景衰减就要慢得多

### 底层：短期记忆

context window，容量有限，任务结束就清空。

在一次任务重，靠它记住中间状态





### 规划模块

就是拆解目标，拆解成子任务task

##### 策略A：

先计划，后执行





##### 策略B：

边执行，边规划。根据每步结果动态调整，计划修正。



### 规划模块的底层其实依赖的是LLM的推理能力，如何提升推理能力？

#### CoT

Chain of thought思维链，让模型把思考过程写出来，而不是输出最终答案

可以在prompt中写一句：let's think step by step

这样每一步推理的输出会成为下一步推理的输入。

#### ToT

Tree of thought思维树。

不是走一条线性的推理链，而是在每个推理节点上展开多个可能的分支，评估每个分支的质量，然后选出最优的路径继续往下走



### 两种运作模式

#### Plan and execute模式

先规划后执行。

缺点是：如果中间某一步的结果和预期不一样，原来的计划就需要重新调整



#### ReAct模式

边执行边规划。

缺点是容易走偏。因为每一步都是局部最优决策，有时候会忽略整体目标



因此，要把两种模式结合。先做一个粗略的计划，确定大方向，执行过程中再根据反馈，动态微调

4.Orchestrator and workers
