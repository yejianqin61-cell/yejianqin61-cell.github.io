这题本来我是想着先用一个unordered_map记录一下每个数字的出现次数

然后找一个最小的数字，然后一次次+1来计算序列长度。但是这样，没有做到合理剪枝。

1. 比如数组是 `[0, 1000000000]`，`mini=0`，那么 `tail` 会从 1 一直递增到 10 亿，循环执行 10 亿次，而 `index` 几乎不变（因为中间没有元素），所以 `index<size` 长期成立 → **超时**。
2. 另外当数组元素范围很大（如 `[-1000000000, 1000000000]`）时，`tail` 逐一遍历同样会跑极多次



所以遗憾超时。这样做其实没有很好的发挥哈希表的功效。于是我看了一下讨论区，有人说，要引入一个概念叫做排头兵，愚以为妙绝。



```cpp
#include <unordered_map>
class Solution {
public:
    int longestConsecutive(vector<int>& nums) {
        
        unordered_map <int,int> mp;
        int size=nums.size();
        if(size==0)return 0;
        int mini=10000000;
        for(int i=0;i<size;i++){
            mp[nums[i]]++;
            mini=min(nums[i],mini);
        }
        int length=1;
        for (auto num: mp) {
                if(mp.count(num.first-1)){
                    continue;
                }else{
                    int cur=num.first;
                    while(mp.count(cur)){
                        cur++;
                    }
                    length=max(length,cur-num.first);
                }
            }
        return length;
    }
};
```

首先就是unordered_map来记录每个是否出现。

然后！遍历这个unordered_map，如果这个元素-1不在哈希表里，那么说明这个元素就是排头兵。这个时候再内置一个while循环，往下去寻找这个排头兵最远能有多大的顺子。然后再更新length。



如果元素-1在哈希表里怎么办，说明它不是排头兵。那不用管，直接往下遍历。

为什么不用管，因为这个元素会出现在别的排头兵的某个序列里，会被计算进去。因此不用管。

**这就是合理剪枝**

Coding Worker 是项目经理，它通过 SDK 向 DSH 发出指令；真正执行 Agent 任务的是 DSH Runtime。

这也解释了为什么文档要求 SDK 和 CLI 使用精确匹配的版本。

另外，根据文档锁定的上游版本，DSH 根包要求 Node.js 24.9.0 或更新，而 ERP API 仍是 Node.js 22。因此独立 Worker 还能避免升级生产 API 运行时带来的兼容性风险。



1. SDK 是 DSH 提供的客户端库。 它负责启动、连接和控制 Harness Runtime，包括发送任务、管理会话、接收事件及关闭进程。它不只是启动器。
2. Coding Worker 是我们自己的架构概念。 DSH 并没有要求必须存在这个叫 Coding Worker 的组件。我们自己实现它，负责作业调度、生命周期管理、候选产物收集等。
3. Builder 和 Validator 都计划运行在 Harness Runtime 内部。 它们通过 `dsh-subagent` 和 `spawn-in-process` 机制执行，是拥有独立会话上下文的子 Agent，而不是两个独立的操作系统进程。

### 4、Profile、Patch、Preset 有什么区别？

这三个词非常容易混淆，我们拿实际开发情景来区分。

Profile — 选择运行时的基础配置

例如选择 `sdk` profile，让 Harness 按适合 SDK 控制的方式启动。

文档特别强调：不能直接使用 `sdk-minimal`，因为它不包含本方案所需的 Subagent 能力。

Patch — 修改基础插件组合

以 `sdk` profile 为基线，禁用 Web 搜索、遥测等不需要的组件，加入 ERP 专用编排插件。

它调整的是 Harness Runtime 的组成。

Preset — 配置不同 Agent 的行为与工具面

Builder 需要读代码、写候选文件、运行测试；Validator 需要审查代码、设计测试和生成报告。

因此二者可以使用不同的 preset。

注意，文档没有给出最终 Builder/Validator preset 的完整配置。我们现在讨论的是它们的设计职责，具体工具集合仍属于 Phase 1 待验证事项。

##### 一、Profile 到底是什么意思？

在 DeepSeek Harness 中，你可以把 Profile 理解为一套预定义的 Runtime 组件配置方案。

注意，不是 Agent 的人设，也不是 System Prompt。

假设 Harness 提供了这些组件：

DSH 可组合的组件（示意）

Model

模型调用

Session

会话管理

Tools

工具调用

Subagent

子 Agent 管理

Shell / FS

命令与文件操作

SDK Server

对外通信

一个 Harness Runtime 不一定需要启用所有组件。

例如：

- 交互式 Coding Agent 需要终端交互组件。
- 通过 SDK 操控的 Agent 需要 JSON-RPC Server。
- 需要 Builder/Validator 协作的系统则必须具备 Subagent 能力。

因此，DSH 使用 Profile 来决定以什么组件组合启动。

在我们的文档中，使用的是：

```
dsh --profile sdk
```

根据源码核查，`sdk` Profile 由 `dsh-base` 和 `dsh-sdk-app` 组成，后者提供 SDK JSON-RPC Server，并禁用 Harness HMR。而 `sdk-minimal` 不具备本方案需要的 Subagent 能力。



### Profile、Patch、Preset 三者的区别

| 概念    | 解决的问题                 | Clay 中的例子                                              |
| ------- | -------------------------- | ---------------------------------------------------------- |
| Profile | Runtime 加载哪些基础能力？ | 选择 `sdk`，使 Harness 能被 SDK 操控                       |
| Patch   | 如何修改这套组件组合？     | 禁用不必要的联网和遥测插件，加入 Clay 编排插件             |
| Preset  | 某个 Agent 应如何工作？    | Builder 使用偏向代码开发的工具配置，Validator 使用审查配置 |

Profile 定义 Runtime 的基础形态，Patch 调整 Runtime 的组件组合，Preset 配置 Agent 的行为与可用工具。

### 5.Subagent：这是 Clay 最核心的复用能力

文档第 40–41 行提到：

- `dsh-subagent`
- `spawn-in-process`
- `ctx.subagents.startActivation()`

我们逐个看。

1. `dsh-subagent`

负责 Harness 内部的子 Agent 机制。

2. `spawn-in-process`

**意味着子 Agent 可以在同一个 Harness 进程内运行，而不是必须为每个子 Agent 创建新的操作系统进程。**

3. `ctx.subagents.startActivation()`

这是 Harness 内部供插件程序化启动子 Agent 的接口。

对于 Clay，我们希望最终有这样的执行过程：

```
ERP 发出构建任务
        │
        ▼
Clay 编排插件
        │
        ▼
startActivation(Builder)
        │
        ▼
Builder 编写候选工具
        │
        ▼
确认 Builder 产物
        │
        ▼
startActivation(Validator)
        │
        ▼
Validator 审查 + 测试
        │
        ▼
Worker 收集证据
        │
        ▼
ERP 独立发布门禁
```

##### 细节 A：独立 Context 不等于独立 Process

Builder 与 Validator 可以有独立的会话上下文，Validator 不必继承 Builder 的完整对话历史。

但由于使用 `spawn-in-process`，它们仍然可以共享进程与容器权限。

因此，不能认为“Validator 的 preset 没有写文件工具”就能从操作系统层面保证它无法写文件。

Agent Context 解决上下文管理问题，容器隔离才承担最终的系统权限边界。

##### 细节 B：我们还没有证明可以强制调度子 Agent

这个问题甚至比独立 Context 更重要。

当前方案希望由 Clay 的 Cordis 插件调用 `ctx.subagents.startActivation()`。

但是 SDK 公开协议没有提供一个可以由 Worker 直接调用的 `startSubagent()` RPC。

因此我们必须实验验证：自定义插件能否在 `sdk` profile 里取得有效的父会话，并且可靠地响应构建任务。

这就是 Phase 1 非常重要的技术风险，而不是已经解决的问题。



## BuildProgress

意思是：Coding Worker 向 ERP 汇报执行进度。

这是你之前接触的 SSE 和事件驱动机制可以发挥作用的地方。

假设 Harness 正在执行一个 Builder → Validator 工作流。

我们可能收到这样的事件：

一次构建任务的事件序列（示意）

1. Builder Started

   activation_id: act_101 · Builder 开始开发工具

2. Builder Finished

   act_101 · 候选代码和单元测试已生成

3. Validator Started

   activation_id: act_102 · Validator 开始独立审查

4. Validator Finished

   act_102 · 审查结果和测试报告已生成

5. BuildCandidate Submitted

   Worker 交付候选包，等待 ERP 独立门禁检查

原文给 `BuildProgress` 设计了这些字段：

`request_id`、`attempt_id`、`capability_id`、`role`、`activation_id`、`state`、`seq` 和时间戳。

这里最需要理解的有三个 ID。

### 1. request_id：这是哪一项需求？

例如 `req_001`。

一个逻辑需求可能会因为失败而进行多次构建尝试，但它们仍然属于同一个 `request_id`。

### 2. attempt_id：这是第几次构建尝试？

假设第一次构建中 DSH 进程崩溃了。

Worker 重启一套新的 Harness Runtime 再尝试。

此时：

```
request_id = req_001
    │
    ├── attempt_id = attempt_001
    │       └── Harness 崩溃
    │
    └── attempt_id = attempt_002
            └── 重新构建
```

你看，同一个需求可以有多个 Attempt。

根据文档，每个 Attempt 对应一次独立的 Harness 进程运行，重试使用新的候选目录。这样就不会把上一次失败留下的文件误当成当前的合法产物。

### 3. activation_id：这是哪个子 Agent 的执行？

假设我们需要开发两个工具，每个工具都需要 Builder 和 Validator。

那么可能出现：

```
request_id: req_001
    │
    └── attempt_001
           │
           ├── capability_A
           │      ├── Builder  → act_101
           │      └── Validator → act_102
           │
           └── capability_B
                  ├── Builder  → act_103
                  └── Validator → act_104
```

这就是为什么需要不同层次的 ID。

`request_id` 管逻辑需求，`attempt_id` 管构建尝试，`capability_id` 管具体工具，`activation_id` 管子 Agent 执行实例。

至于 `seq`，它用于处理事件的重复与乱序。

例如 ERP 重复收到序号 5 的进度事件，应该识别并去重，而不能重复推进状态。

这就是 Agent 可观测性（Observability）和可靠运行管理的基础。

还有一个安全要求：BuildProgress 只应向 ERP 的进度接口提供适当的状态和稳定错误码，不能把 Agent 的内部 Prompt、ERP 源码或者敏感业务数据直接透传到 SSE。

# Coding Run 的确定性编排



我们已经知道，Coding Worker 会通过 SDK 启动 Harness Runtime，里面运行 Builder 和 Validator。

但现在出现一个新问题：

如何保证 Builder 和 Validator 按我们要求的顺序工作，而不是让模型自己随意决定？

这就是本节要解决的问题。

## 一、先理解什么叫「确定性编排」

假设我们有一个母 Agent（Orchestrator），负责管理 Builder 和 Validator。

我们可以给母 Agent 写一段 System Prompt：

> 你是 Coding Orchestrator。收到任务后，必须先调用 Builder 开发工具，再调用 Validator 审查。如果审查失败，要求 Builder 修复。

这样看上去很合理，对吧？

但问题是，Prompt 不是程序级约束。

LLM 可能不遵守指令，也可能误认为 Validator 已经执行过，或者在复杂任务中遗漏某一步。

因此，文档提出：

> 目标拓扑为 `capability[i] → Builder[i] → Validator[i]`；多个 Builder 可以并行，不同工具的 Validator 在各自 Builder 完成后即可开始。批次发布要求全部 Validator 通过，不能部分激活。
>
> business-query-agent-deepseek-harness-sdk-phase1-2026-10-29.md

这里的“确定性”不是要求 Agent 每次生成完全一样的代码。

而是要求无论模型内部怎么思考，都不能绕过规定的执行流程。

这是两个不同层次：

| 层次                         | 是否允许模型自主决策 |
| ---------------------------- | -------------------- |
| 如何阅读源码、实现工具       | 允许                 |
| 如何设计测试用例             | 允许                 |
| 什么时候必须运行 Validator   | 由程序约束           |
| Validator 失败后能否直接发布 | 程序禁止             |
| 是否超过最大返工次数         | 由程序判断           |

所以可以形成一个重要的架构原则：

模型负责非确定性的开发工作，程序负责确定性的流程约束。



#### 这里有两个要求。

第一，跨工具可以并行。

Builder A 和 Builder B 可以同时工作。

当 Builder A 完成后，Validator A 就可以开始审查，不必等待 Builder B。

第二，同一个工具必须遵守依赖顺序。

Validator A 必须在 Builder A 生成待审查产物之后才能执行。

这本质上是一个有向无环依赖图（DAG），非常接近工作流调度系统中的任务编排。

##### 如果 Validator A 通过，Validator B 失败呢？

根据文档，不能只发布工具 A。

因为原方案采用的是批次整体通过的原则。

这有点像数据库事务中的 All-or-Nothing 思想，不过这里是发布策略上的类比，并不表示已经实现了数据库事务。









### Step 1：Worker 创建独立运行环境

文档要求 Worker 为每个构建批次创建：

- 独立的 `dshHome`
- 候选工具目录
- Harness 进程
- 版本和配置哈希记录

为什么？

因为我们希望每一次构建都具有可追踪、可复现的运行环境。

假如一个 Coding Run 失败了，我们不能让它留下的文件污染下一个构建批次。

这里的 Worker 是整个构建作业的生命周期管理者。

### Step 2：启动 Builder，再启动 Validator

文档提出使用 ERP 专用 Cordis 插件，在受管理的父会话下调用：

```
// 概念示意，不是可直接运行的完整 DSH API 调用
ctx.subagents.startActivation({
  delivery: 'caller',
  // 其他必要的启动参数
});
```

其中最重要的就是：

```
ctx.subagents.startActivation()
```

你可以把 Activation 理解为一次子 Agent 执行实例。

每次启动会得到可以用于跟踪该次执行的 Activation 信息。

而 `delivery: 'caller'` 是文档指定的交付模式。这里先理解为通过调用方处理子 Agent 的结果；更精确的返回与事件语义，需要在 Phase 1 实测。

插件首先启动 Builder，等待对应产物，然后启动 Validator。

这里还要求每个 Builder 写入自己的候选子目录，防止两个 Builder 并行时相互覆盖文件。

### Step 3：Validator 审查与返工

Validator 不只是让模型看一眼代码。

文档要求它编写对抗用例、审查报告，并在发现问题时要求 Builder 修复。

例如：

Builder 实现了一个员工产量查询工具。

Validator 发现：

> 这个工具传入任意订单号时都能查询数据，没有正确约束当前用户允许访问的订单。

这时需要让 Builder 修改，并重新测试、重新审查。

文档特别要求：返工轮次必须有上限。

否则 Builder 和 Validator 可能陷入无止境的互相修改。

而且，Validator 通过并不代表正式验收通过。Worker 仍需要在子 Agent 之外运行确定性检查。

### Step 4：Worker 收集执行证据

这里出现了几个 DSH 的技术名词：

`subagent.started`、`subagent.finished`、`session.event/status`、`session/wait`。

你可以先这样理解：

| 接口或事件             | 作用                              |
| ---------------------- | --------------------------------- |
| `subagent.started`     | 子 Agent 开始执行的证据           |
| `subagent.finished`    | 子 Agent 执行结束的证据           |
| `session.event/status` | 跟踪会话事件与状态                |
| `session/wait`         | 等待受管理的后代 Agent 完成       |
| `run().finalResponse`  | 根 Agent 返回的最终文本，仅作诊断 |

这里有个容易踩的坑：

根 Agent 进入 idle，不代表所有子 Agent 都已经完成。

因为 SDK 的 `run()` 主要等待根 Agent 下一次进入空闲状态。

所以在这种多 Agent 系统中，不能只看 `run()` 是否返回。

还要确认受管理的子 Agent 是否结束、候选文件是否存在，以及证据是否齐全。









# Profile、隔离与数据边界

我们如何让一个拥有 Shell、文件读取和代码修改能力的 Coding Agent，在不破坏 Dilee ERP 生产系统的前提下工作？

## 一、先理解为什么需要隔离

想象一个场景。

现在 Dilee ERP 已经在工厂使用了。我们把 Coding Agent 接入系统，允许它阅读代码并生成工具。

某天，Builder 为了搞懂数据库结构，决定执行一条 Shell 命令。

它不小心删除了某个文件，或者读取了包含数据库密码的 `.env`。

更严重的情况是，它生成的工具包含了绕过权限系统的数据库查询。

这里我们面临两类风险：

1. 构建阶段的风险：Coding Agent 读到了不该读的数据，或修改了不该修改的文件。
2. 运行阶段的风险：生成的业务工具被发布后，访问了不该访问的数据。

第 71–79 行的设计，就是针对这两类风险建立边界。

## 二、第一层：SDK 进程环境隔离

原文第 73 行：

> 使用 `profile: 'sdk'` 与固定的 `patches`；`env` 显式构造完整子进程环境，不继承 API 进程的数据库、Cookie、部署和插件凭据。

我们先看一个熟悉的 Node.js 概念：

```
process.env
```

你应该知道，Node.js 可以通过它读取环境变量。

比如：

```
const databaseUrl = process.env.DATABASE_URL;
const apiKey = process.env.MODEL_API_KEY;
```

假如 ERP 的 API 进程持有：

```
DATABASE_URL=postgresql://...
JWT_SECRET=...
MODEL_API_KEY=...
```

如果我们不加限制地把这些环境变量传给 Harness 进程，那么 Coding Agent 所在的运行环境就可能拥有不必要的秘密。

因此，我们希望 SDK 启动 Harness 时，使用显式构造、尽可能最小化的环境变量集合。

Dilee ERP API

持有业务数据库连接和生产凭据

独立 Worker 环境 · 仅提供必要变量

Coding Worker

构造受限的 Harness 进程环境

允许必要的模型调用配置

不提供生产数据库凭据

不提供 ERP 用户令牌

不提供无关部署和插件密钥

Harness Runtime

只接收受限的子进程环境

注意，不继承环境变量只是第一道防线。如果密钥仍然存在于可读取的文件中，或者进程通过其他途径能访问生产服务，仍然有泄露风险。

因此后面还需要容器、文件系统和网络隔离。

### 这里还有三个配置字段

原文同时提到：

- `dshHome`：Harness 使用的独立 Home 数据目录。
- `processCwd`：Harness 子进程的当前工作目录。
- `patches`：用于调整 Harness 插件配置的补丁。

文档要求每个构建作业使用独立的 `dshHome`、工作目录和候选文件区域。

这是为了减少不同构建任务的状态与文件相互污染，但独立目录本身不是安全沙箱。

另一个细节是版本锁定。

原文固定 SDK 和 CLI 为 `0.2.2-alpha.2`，并说明截至 2026 年 10 月 29 日，npm 两个包的默认 `latest` 标签并不一致。

这就是为什么不能随便：

```
npm install @deepseek-ai/dsh-sdk-client
```

然后假设它会自动搭配兼容的 CLI。

我们要锁定精确版本并验证对应关系。

## 三、第二层：裁减 Harness 的能力

这是第 75 行的内容。

前面我们已经学过：

- Profile 决定 Runtime 的基础组件组合。
- Patch 可以调整其中的插件。

现在这些知识开始发挥作用。

DSH 是一个通用 Coding Agent Harness，可能有很多组件。

但 Clay 的 Coding Agent 不需要全部能力。

文档提出的第一版 Patch 候选，包括禁用：

| 组件                             | 为什么考虑禁用             |
| -------------------------------- | -------------------------- |
| `session-log-deepseek`           | 避免额外的会话日志上传路径 |
| `session-telemetry-otel`、`otel` | 减少不需要的遥测输出       |
| `web`、搜索、抓取等组件          | 限制不必要的联网能力       |
| `tool-plugin-manager`            | 避免 Agent 自行管理插件    |
| 非必需的 schedule、交互工具      | 缩小可用能力范围           |

同时保留 SDK Server、Subagent、Spawn、必要的 Shell/FS、Session 和 Model 能力。

这些都是候选配置，不是已经验证成功的最终插件清单。

为什么？

因为插件可能存在依赖关系。

禁用某个插件，可能导致其他必要组件无法初始化。

所以文档要求利用：

```
dsh --profile sdk --dump-config
```

检查最终配置，再做启动 Smoke Test（冒烟测试）。

上面的命令用于理解原文中的配置检查思路；实际使用时，还需要附带我们自己的 Patch 配置。

### 一个特别需要注意的风险

即使关闭 `session-log-deepseek`，也不等于源码绝对不会离开容器。

Coding Agent 调用外部模型时，提交给模型的上下文仍可能包含 ERP 源码片段。

这正是原文要求提供经过净化的源码快照的原因。

例如包含密码、客户隐私或生产数据的内容，不应该出现在模型可读取的源码视图中。

## 四、第三层：真正的沙箱——容器隔离

这是今天最重要的知识点。

原文第 77 行强调：

> Harness 内建 sandbox 主要管文件影响，不能约束网络和进程可见性。

意思是，我们不能把 DSH 的内建 Sandbox 当成完整的操作系统安全边界。

为什么？

因为 Coding Agent 会使用 Shell。

Shell 可以执行各种操作系统命令。

而 Preset 只是在 Agent 层面控制它能看到或调用哪些工具，并不必然限制底层进程能够访问的资源。

因此，生产环境需要更外层的容器隔离。

### 我们希望得到这样的环境

可丢弃的构建容器

/erp-source

只读

经过净化的 ERP 源码快照。可阅读，但不能修改

/candidates

可写

Builder 只能在允许的候选产物区域写入工具代码

/test-workspace

可写

运行受控测试和临时构建任务

不挂载的资源

生产数据库、`.env`、客户上传文件、备份、密钥、生产用户令牌

示意目录仅用于说明访问边界，并非文档固定的容器路径。

这就很容易理解了。

Builder 即使执行了某条错误命令，也不应该因此获得修改 ERP 生产源码或读取生产数据库的权限。

因为这些资源根本没有被提供给它。

但要注意：

只读挂载不代表无法读取其中的敏感内容。

所以必须先清理源码快照中的秘密，再交给 Harness。

同时还需要在操作系统和容器层控制网络访问、进程权限、资源消耗与运行时限。

文档还明确说，构建测试默认断网，生产 Worker 只允许必要的模型服务和固定依赖源出口。

business-query-agent-deepseek-harness-sdk-phase1-2026-10-29.md



### 为什么 Shell 必须保留？

你可能会问：

既然 Shell 很危险，干脆禁用不就行了吗？

问题是我们要做的是 Coding Agent。

它可能需要：

- 运行 TypeScript 编译。
- 执行单元测试。
- 检查文件差异。
- 验证生成的模块是否能被导入。

如果完全禁用 Shell，Agent 的工程能力会受到很大限制。

因此我们的思路不是简单地禁止一切，而是：

保留必要的开发能力，把能力的作用范围限制在受控环境中。

这是安全工程中很重要的设计思想：**最小权限原则（Principle of Least Privilege）。**

## 五、第四层：业务数据也要隔离

接下来是原文第 79 行。

这一段容易被忽略，但对于 Dilee ERP 极其重要。

文档要求：

> 候选包只能通过宿主提供的受限只读数据入口取业务数据；不得直接拥有 Prisma client 或原始 SQL 通道。

为什么要如此严格？

我们先看原本的业务工具执行路径：

```
Query Agent
    │
    ▼
Tool Executor
    │
    ├── 检查用户角色
    ├── 验证查询参数
    ├── 验证订单范围
    └── 执行受控数据查询
```

现在假设 Builder 生成了一个新工具，里面直接使用：

```
// 这是应该被拒绝的候选实现示例
const records = await prisma.productionRecord.findMany();
```

这个例子只是示意，具体 Prisma 模型名称并非文档提供的真实名称。

为什么不能接受？

因为新生成的工具可能绕开原本的权限入口。

如果未来工具具有数据库直接访问能力，那么它可能查询超出当前用户权限范围的数据。

所以原文要求工具只能通过受限的数据入口访问业务数据。

允许的业务查询路径

Generated Business Tool

ERP 受限只读数据入口

验证角色 · 订单范围 · 查询参数

ERP 数据访问层

执行符合权限的查询

拒绝的路径

Generated Tool → Prisma Client / Raw SQL → Database

并且，工具运行结束后，还要限制：

- 最终返回哪些字段。
- 最多返回多少行数据。
- 最大返回字节数。
- 是否保留数据来源信息。

也就是说，不能因为 Tool 是内部 Coding Agent 生成的，就默认它可信。

生成的代码必须继续受到 ERP 的业务权限模型约束。

这也是 Clay 未来进入真实企业环境的基本前提。

## 六、这四层防护解决了不同的问题

| 防护层             | 主要防范什么                          |
| ------------------ | ------------------------------------- |
| SDK 环境变量隔离   | Harness 意外获取生产密钥              |
| Profile / Patch    | Runtime 加载不必要的危险能力          |
| 容器隔离           | Coding Agent 越界访问文件、网络和进程 |
| ERP 数据与发布边界 | 生成的工具越权访问业务数据            |

这四层不能互相替代。

尤其记住：

Preset 是 Agent 层的行为限制，容器是系统层的权限边界，ERP Executor 是业务层的权限边界。
